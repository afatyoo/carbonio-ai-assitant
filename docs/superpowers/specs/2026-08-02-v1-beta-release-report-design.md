# Carbonio AI Assistant v1 Beta Release Report Design

**Date:** 2026-08-02

**Target package version:** `1.0.0-beta.1`

**Target Git tag:** `v1.0.0-beta.1`

**Release class:** GitHub prerelease

**Audience:** Carbonio administrators, pilot users, contributors, security reviewers,
and operators evaluating the addon for a controlled deployment.

## Purpose

Promote the completed core Carbonio AI Assistant work from the `0.0.3-rc.*` sequence
to a clearly documented `1.0.0-beta.1` prerelease. The release must explain the whole
implemented product, not only the delta from RC19, while remaining explicit that the
production-ready vector and user-workspace RAG program is deferred and that several
external UAT gates are not complete.

## Release Artifacts

The implementation will produce all of the following from one exact Git commit:

1. `docs/releases/v1.0.0-beta.1.md` as the authoritative detailed release report.
2. A `CHANGELOG.md` entry summarizing the beta and linking to the detailed report.
3. Root UI package version `1.0.0-beta.1`.
4. Gateway package and gateway lockfile version `1.0.0-beta.1`.
5. Release archive `carbonio-ai-assistant-v1.0.0-beta.1.tar.gz`.
6. SHA-256 checksum asset generated by the existing packaging workflow.
7. Annotated Git tag `v1.0.0-beta.1` after exact-commit CI succeeds.
8. A GitHub prerelease whose body uses the detailed report instead of relying only on
   generated commit titles.

No stable `v1.0.0` claim will be made by this work.

## Authoritative Evidence Sources

The report must be derived from and cross-checked against:

- repository history from `v0.0.1` through `v0.0.3-rc.19`;
- `CHANGELOG.md`, `README.md`, gateway/deployment documentation, and UAT runbook;
- current code and self-test coverage, rather than planned intent alone;
- GitHub CI and release workflow results for the candidate commit;
- public release artifact metadata and embedded `release.env`;
- deployed Carbonio server state, strict smoke output, PostgreSQL reconnect evidence,
  structured gateway logs, audit references, and authenticated Webmail UAT;
- Obsidian Plan 01 and Pilot UAT records for known external gates and explicitly skipped
  actions.

Claims without one of these evidence types must be omitted or labeled as unverified.

## Detailed Report Structure

### 1. Executive Summary

Explain what Carbonio AI Assistant is, why the beta exists, the supported controlled-pilot
scope, and the meaning of `beta.1`. State that the UI is a standalone Carbonio
microfrontend and the AI gateway is a separate loopback-only Node.js service proxied by
Carbonio Nginx.

### 2. Release Highlights

Provide a compact high-level list covering:

- native Carbonio sidebar integration and ChatGPT-style assistant experience;
- Carbonio i18n-aware English and Indonesian UI;
- provider presets, custom endpoints, model discovery, allowlists, and free-model testing;
- server-side PostgreSQL conversation history;
- Carbonio-aware email and calendar tools with confirmation cards;
- security/admin controls, observability, packaging, and repeatable deployment;
- curated official-documentation knowledge retrieval with citations.

### 3. User Experience and UI

Document the robot sidebar icon, assistant route, responsive layout, theme compatibility,
conversation history, rename/delete/undo flows, hover actions, model selector, settings
screen, action previews, accessible controls, streaming responses, loading states,
localized errors, and request-ID visibility.

### 4. Provider and Model Configuration

Document OpenRouter, OpenAI, Anthropic/Claude, DeepSeek, and custom OpenAI-compatible
provider handling; preset endpoints; administrator-owned credentials; API-key
non-disclosure; model discovery and allowlisting; user model preferences; OpenRouter free
model use; and the production privacy lock (`data_collection=deny`, `zdr=true`). Avoid
claiming that every third-party provider was live-tested when only its configuration path
was implemented.

### 5. Conversation History and PostgreSQL

Document owner-isolated history, pagination, search, rename, soft delete, restore/undo,
daily quota/token usage, preferences, versioned migrations, optional encryption,
SQLite-only development fallback, PostgreSQL production enforcement, and reconnect
survival. Include the evidence that gateway health remains PostgreSQL-backed.

### 6. Tool Framework and Safety Model

Explain tool registry/schema validation, permission scopes, `READ`/`WRITE`/`DESTRUCTIVE`
risk levels, exact-target resolution, bounded results, confirmation previews, one-time
tokens, idempotency keys, owner-scoped structured audit entries, result references,
timeouts, cancellation, and output-size limits. State that preview generation does not
run the mutation.

### 7. Email Capabilities

Inventory every implemented email capability and its boundary:

- bounded email search;
- exact message retrieval;
- thread retrieval and summary;
- attachment metadata inspection without uncontrolled content disclosure;
- new/reply draft creation;
- draft update;
- forward-as-draft;
- send email with recipient/CC/BCC/subject/body preview;
- mark as read;
- add tag;
- move email;
- permanent delete as a separate destructive tool.

Document the Carbonio SOAP operations used (`Search`, `GetMsg`, `GetConversation`,
`SaveDraft`, `SendMsg`, and `MsgAction`) and the rule that a draft never auto-sends.

### 8. Calendar, Meeting, and Contact Capabilities

Document bounded appointment search, exact appointment retrieval, contact/GAL attendee
resolution, free/busy checks, timezone conversion, multiple meeting-slot suggestions,
calendar draft/create flow, version-aware updates using `ms`/`rev`, before/after diffs,
invitation sending, cancellation, recurring-mutation rejection, and the associated
Carbonio SOAP operations.

### 9. Carbonio Documentation Knowledge MVP

Document the curated lexical index for official Carbonio email API guidance, local
retrieval, source titles/URLs/version metadata, citation rendering, and the boundary that
this is documentation grounding—not production-ready mailbox/files vector RAG.

### 10. Security, Privacy, and Administration

Cover Carbonio-session verification, CSRF/origin checks, loopback binding, Nginx security
headers, account/group/domain policy, tool permissions, write kill switch, emergency addon
disable, daily quotas, admin-only provider settings, credential-at-rest handling, output
sanitization, data minimization/redaction, disclosure copy, audit viewer, metrics, and
provider health status.

### 11. Reliability and Observability

Cover structured request IDs across UI/gateway/provider/SOAP boundaries, retries limited
to transient failures, timeout/cancel propagation, provider circuit breaker, health
endpoint, metrics, PostgreSQL pool error handling, process survival across PostgreSQL
restart/disconnect, and user-visible localized errors.

### 12. Packaging, Service, and Deployment

Document the versioned archive, checksum, embedded version/commit/Node runtime, installer,
uninstaller, API-key helper, PostgreSQL setup/backup/restore helpers, rollback script,
systemd service, loopback gateway, Carbonio Nginx integration, Iris component registry,
versioned UI/gateway releases, atomic symlink switching, pre-deploy backup, and strict
smoke verification.

### 13. CI/CD and Verification Matrix

Provide a table mapping each gate to evidence:

- ESLint;
- TypeScript type-check;
- UI/i18n/accessibility contracts;
- deployment smoke contracts;
- gateway syntax and complete self-tests;
- PostgreSQL disconnect/reconnect integration;
- production UI build;
- dependency audits;
- secret scan;
- tag/version equality;
- package checksum and embedded-commit verification;
- server-side smoke/regression;
- authenticated Webmail UAT.

The final beta commit and run IDs will be inserted only after they exist.

### 14. Complete Closed-Bug Ledger

List every verified bug or unsafe behavior closed during the project. Each entry must
contain symptom, root cause, resolution, regression/evidence, and affected release where
known. At minimum the ledger will include:

1. JSON parsing failed when an HTML error/login page was returned.
2. Gateway route/method mismatch produced HTTP 405.
3. Successful streaming requests did not render the AI answer.
4. Conversation history stored only in browser state and disappeared.
5. Chat history actions/delete affordance were invisible or inconsistent in Webmail.
6. Robot icon and assistant layout rendered incorrectly inside Carbonio dimensions/theme.
7. i18n strings diverged between English and Indonesian.
8. Provider endpoints required manual URLs instead of safe presets/custom fallback.
9. API credentials risked exposure or misleading browser display.
10. Request failures lost their request ID at the SSE/UI boundary.
11. Calendar search needed the correct Carbonio calendar scope.
12. Live `GetAppointment` returned array-shaped fields not handled by fixtures.
13. Recurring calendar mutations were not explicitly rejected at all entry points.
14. OpenRouter privacy behavior depended on configuration instead of a production lock.
15. PostgreSQL idle-client errors could terminate or destabilize the gateway.
16. Production smoke could accept SQLite history instead of failing closed.
17. Release tags did not originally enforce full CI/security/PostgreSQL parity.
18. Email/calendar mutation criteria could resolve ambiguous or changed targets.
19. Explicit item IDs captured terminal sentence punctuation (`435.`).
20. Folder-qualified explicit IDs such as `email Inbox ID 440` were rejected.
21. A source folder qualifier could be mistaken for a move destination.
22. Connector words inside quoted subjects could confuse move destination parsing.
23. Multiple destinations such as `Inbox or Trash` could select the first silently.
24. Bare numeric move destinations broadened targeting unsafely.

The implementation audit may add further verified issues from earlier changelog entries,
but it may not invent bugs merely to make the list longer.

### 15. Live UAT Results

Record authenticated evidence without confidential mailbox content, including provider
round-trip, history persistence, settings/admin boundaries that were testable, exact-ID
previews, fail-closed ambiguous targeting, Send ID `439`, Inbox ID `440`, mark-read audit,
move-to-Trash audit, PostgreSQL restart survival, and conversation delete/undo. The report
must distinguish preview-only tests from mutations that were actually approved and run.

### 16. Known Limitations and Open Gates

State these without presenting them as code failures:

- pilot approver/sign-off is not recorded;
- logout/login repetition is unverified because the operator lacks the pilot password;
- authenticated Firefox/narrow-browser evidence is incomplete;
- non-admin Settings boundary needs a non-admin account;
- the pilot mailbox is too small for large-mailbox performance acceptance;
- live attachment coverage lacks a dedicated test attachment;
- separate staging, Carbonio upgrade rehearsal, and failover/replica environments are not
  available;
- `AI-UAT` tag/folder mutation was not completed;
- permanent delete of message `440` and its replay test were explicitly skipped;
- calendar update/invitation/stale-version/cancel/replay mutation lifecycle remains
  unapproved;
- the Carbonio Nginx configuration warns that configured worker connections exceed the
  shell open-file limit, an external host-capacity concern.

### 17. Deferred Scope

Link to the separate production-ready RAG plan and explicitly defer controlled importers,
embeddings, `pgvector`, hybrid retrieval, reranking, per-user/workspace vector isolation,
mailbox/files indexing, retention/deletion propagation, and production RAG observability.

### 18. Installation, Upgrade, Rollback, and Verification Notes

Provide concise commands and precautions for backup, archive checksum validation,
installation, smoke test, service status, rollback, and post-install browser reload. Do not
embed credentials, internal secrets, or a live database URL.

## GitHub Release Body

The release workflow will be changed so `v1.0.0-beta.1` publishes a curated body based on
the detailed report. The GitHub page should lead with highlights and safety status, then
link to or include the detailed sections. Generated commit notes may appear only as a
supplement; they are not the authoritative description.

## Version and Compatibility Rules

- Use `1.0.0-beta.1` in root `package.json`, gateway `package.json`, and gateway
  `package-lock.json` root/package entries.
- Use `v1.0.0-beta.1` for the annotated Git tag and GitHub prerelease.
- Do not alter database schemas solely for the version promotion.
- Do not change runtime behavior except what is necessary to publish the curated release
  body; the beta is built from the already verified RC19 core behavior plus documentation
  and release metadata.
- Preserve Node.js `v22.22.0` in packaged `release.env`.
- Preserve MIT licensing.

## Verification and Release Gates

Before tag publication, the exact beta commit must pass:

1. clean diff and consistent version checks;
2. lint and TypeScript type-check;
3. all UI contracts;
4. deployment smoke self-test;
5. gateway syntax and full self-test suite;
6. PostgreSQL disconnect/reconnect integration;
7. production UI build;
8. dependency audit and secret scan through GitHub CI;
9. package generation and local checksum verification;
10. independent review of the report for unsupported claims and missing known limits.

After tag publication:

1. the release workflow must pass on the exact beta commit;
2. the public archive checksum must verify;
3. embedded version, commit, and Node runtime must match;
4. the tag must dereference to the exact reviewed commit;
5. the GitHub release must be marked prerelease and contain the curated detailed notes.

Deployment of the beta to the Carbonio pilot server is a separate final step. It requires a
fresh PostgreSQL backup, checksum verification on the server, versioned installation,
strict smoke, deployed regression, PostgreSQL reconnect verification, and authenticated
sanity UAT. No additional mailbox/calendar mutation is implied by deployment.

## Success Criteria

This design is complete when a reader can answer all of the following from the release
page and repository report:

- What does the beta implement?
- Which Carbonio operations can it perform, and what confirmations protect them?
- Which production, security, privacy, reliability, and deployment controls exist?
- Which concrete bugs were fixed and how were they verified?
- What was actually tested on the live Carbonio server?
- What remains incomplete, skipped, externally blocked, or deferred?
- How can an operator install, verify, back up, and roll back the beta safely?
