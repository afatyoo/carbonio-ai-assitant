# Carbonio AI Assistant v2.1.0

**Release class:** Full user-scoped Carbonio addon release

**Release date:** 2026-08-08

**License:** MIT

**Support status:** Independent community project. Not developed, certified, endorsed, or supported by Zextras.

## Executive summary

Version 2.1.0 expands Carbonio AI Assistant from the stable Mail, Calendar, history, side
panel, and private RAG foundation into a broad user productivity toolset. The gateway now
registers 74 active user-scoped tools. New capabilities cover message organization, folders,
tags, personal Contacts, calendars, invitation responses, appointment forwarding, alarms,
user-owned sharing, incoming filter rules, sending identities, and signatures.

The chatbot receives an allowlisted tool catalog. It can propose only registered tools for
which the authenticated account has permission. It is instructed never to invent an item ID,
revision, target name, recipient, timestamp, filter definition, or contact field. All draft,
write, and destructive operations still stop at a single-use confirmation preview. Existing
targets are read again after confirmation when the API exposes stable identity or revision
metadata.

This release retains encrypted PostgreSQL conversation history, user-controlled private RAG,
forced row-level security, the separate RAG worker, provider privacy controls, all nine
official Carbonio interface locales, the context-aware side panel, request-correlated audit
records, backup, rollback, uninstall, and systemd services.

## User guide

1. Sign in to Carbonio and open the robot icon from the primary navigation.
2. Select an administrator-approved model.
3. Ask a bounded read request first, such as "List my calendars" or "Show my contacts."
4. For a mutation, identify the exact item shown by the read result. Include its ID and the
   required current metadata when the assistant asks for it.
5. Read the confirmation card carefully. Check the target, current name, recipient,
   destination, permissions, content, and destructive warning.
6. Confirm once only when every field is correct. Reject the proposal and start again if the
   target changed or any field is unexpected.
7. Enable private AI Sources only for data the user is permitted to send to the configured AI
   provider. Use Sync now and wait for a ready state before expecting indexed answers.
8. Use the request ID displayed by the UI when reporting an error to the operator.

Suggested read tests include "List my folders," "List my personal contacts," "List my
calendars," "List my shares," "List my filter rules," "List my identities," and "List my
signatures." Mutating tests must use disposable records and must be reviewed in the full
assistant, not the compact side panel.

## Risk acceptance

Installing, enabling, or using this addon means the operator and participating user accept
the following conditions:

- This is an independent community addon and is not an official Zextras product. Zextras has
  no support, warranty, certification, endorsement, or compatibility obligation for it.
- The operator owns deployment, provider contracting, privacy assessment, retention policy,
  incident response, backups, upgrades, monitoring, and rollback.
- The AI planner is probabilistic. It can propose only allowlisted tools, but users must still
  inspect every confirmation. A confirmation is user authorization for that exact operation.
- Third-party AI providers can receive minimized Carbonio content needed for a request. The
  operator must configure provider privacy controls and obtain any required user consent.
- Destructive tools can permanently remove messages, attachments, calendars, filter rules,
  identities, signatures, tags, shares, or Trash content after confirmation.
- Files and Docs, Chats and rooms, binary attachment understanding, and five Tasks mutations
  are not claimed as supported on the tested server.
- Task reads remain compatibility-gated until authenticated synchronization passes. The server
  rejects the documented task mutation commands with `service.UNKNOWN_DOCUMENT`.
- Large-mailbox capacity, representative retrieval quality, PostgreSQL HA, multi-browser UAT,
  and Carbonio upgrade rehearsal require site-specific acceptance.

Risk acceptance permits controlled use. It does not convert an open gate into verified support.

## Complete closed-bug ledger

### BUG-001 - Tool catalog stopped at Mail and basic Calendar
- **Symptom:** The assistant could not represent most normal user activities.
- **Root cause:** The capability manifest contained planned entries without registered handlers.
- **Resolution:** Registered every target-server-supported user tool and aligned the manifest.
- **Regression/evidence:** Capability self-test reports 74 active tools with exact registry parity.

### BUG-002 - New tools were not selectable by chat
- **Symptom:** Direct tool endpoints existed but natural-language chat could not choose them.
- **Root cause:** The agent used narrow handwritten classifiers only.
- **Resolution:** Added an allowlisted schema-driven AI tool planner for the extended catalog.
- **Regression/evidence:** Intent and catalog tests pass and non-tool prompts do not trigger it.

### BUG-003 - Contact lifecycle was missing
- **Symptom:** Users could search GAL but not manage personal contacts.
- **Root cause:** `GetContacts`, `CreateContact`, `ModifyContact`, and `ContactAction` had no tools.
- **Resolution:** Added list, get, create, update, move, tag, and recoverable delete.
- **Regression/evidence:** Registry, schemas, permission boundaries, and server command probes pass.

### BUG-004 - Contact updates could target stale data
- **Symptom:** A changed contact could be overwritten after an old preview.
- **Root cause:** No exact revision comparison existed.
- **Resolution:** Fetch the contact after confirmation and reject a revision mismatch.
- **Regression/evidence:** Mutation handlers require the exact contact ID and current revision.

### BUG-005 - Contact folder destinations were not verified
- **Symptom:** A move or create could use a stale or invented folder target.
- **Root cause:** Folder metadata was not bound to the confirmation input.
- **Resolution:** Require folder ID and name and revalidate them after confirmation.
- **Regression/evidence:** Folder mismatch paths fail closed before SOAP mutation.

### BUG-006 - Calendar lifecycle management was missing
- **Symptom:** Users could manage appointments but not their calendar folders.
- **Root cause:** Calendar folder APIs were not registered.
- **Resolution:** Added list, create, rename, and permanent delete with exact target checks.
- **Regression/evidence:** Server recognizes `CreateFolder`, `FolderAction`, and `DeleteCalendar`.

### BUG-007 - Invitation responses were missing
- **Symptom:** Users could not accept, tentatively accept, or decline an invite through chat.
- **Root cause:** `SendInviteReply` was absent from the tool boundary.
- **Resolution:** Added a confirmed response tool bound to appointment, invite, revision, and subject.
- **Regression/evidence:** Command recognition and confirmation schema checks pass.

### BUG-008 - Appointment forwarding was missing
- **Symptom:** Users could not forward an appointment to selected recipients.
- **Root cause:** `ForwardAppointment` was not implemented.
- **Resolution:** Added bounded recipients, plain-text body, and exact appointment revalidation.
- **Regression/evidence:** Server command recognition and input bounds pass.

### BUG-009 - Alarm controls were missing
- **Symptom:** Users could not dismiss or snooze appointment alarms.
- **Root cause:** Alarm SOAP operations were not exposed.
- **Resolution:** Added ISO timestamp validation and exact appointment revalidation.
- **Regression/evidence:** Both alarm commands are recognized by the target server.

### BUG-010 - Archive and restore were incomplete
- **Symptom:** Users had to express both actions as generic moves without archive semantics.
- **Root cause:** No dedicated exact-target tools existed.
- **Resolution:** Added archive and restore with message revision plus destination verification.
- **Regression/evidence:** Both tools require confirmation and use bounded `MsgAction` moves.

### BUG-011 - Attachment removal was unavailable
- **Symptom:** Users could list attachments but could not remove one exact attachment.
- **Root cause:** `RemoveAttachments` was not registered.
- **Resolution:** Added permanent removal bound to message revision, part, and filename.
- **Regression/evidence:** Server recognizes the command and the handler revalidates metadata.

### BUG-012 - User-owned sharing was unavailable
- **Symptom:** Users could not inspect or change their own folder sharing.
- **Root cause:** Folder ACL operations were absent.
- **Resolution:** Added share list, grant, revoke, and notification tools.
- **Regression/evidence:** Grant rights are allowlisted and all writes require confirmation.

### BUG-013 - Share listing depended on an unsupported command
- **Symptom:** `GetShareInfo` returns `service.UNKNOWN_DOCUMENT` on the target server.
- **Root cause:** Documentation and target-server capability differed.
- **Resolution:** Read outgoing ACLs and incoming mountpoints through supported `GetFolder` data.
- **Regression/evidence:** Safe server probe identified the incompatibility before release.

### BUG-014 - Filter rules were not manageable
- **Symptom:** Users could not inspect or manage personal incoming filters.
- **Root cause:** Mail filter APIs had no registered boundary.
- **Resolution:** Added list, create, update, and delete with a live full-rule re-read.
- **Regression/evidence:** Target server recognizes `GetFilterRules` and `ModifyFilterRules`.

### BUG-015 - Filter mutations could overwrite an unseen rule set
- **Symptom:** A replacement request could erase concurrent changes.
- **Root cause:** `ModifyFilterRules` replaces the ordered collection.
- **Resolution:** Fetch current rules after confirmation and apply one named change to that set.
- **Regression/evidence:** Missing, duplicate, or changed named targets fail closed.

### BUG-016 - Sending identities were not manageable
- **Symptom:** Users could not list or update personal sending identities.
- **Root cause:** Account identity APIs were not registered.
- **Resolution:** Added list, create, update, and delete under user preference permissions.
- **Regression/evidence:** All four identity commands are recognized by the target server.

### BUG-017 - Signatures were not manageable
- **Symptom:** Users could not maintain plain-text or HTML signatures through the assistant.
- **Root cause:** Signature APIs were absent.
- **Resolution:** Added list, create, update, and delete with exact ID and name checks.
- **Regression/evidence:** All signature commands are recognized and schemas bound content type.

### BUG-018 - New domains lacked permission policy scopes
- **Symptom:** Registered tools could be denied even for an enabled user.
- **Root cause:** Security policy knew only Mail and Calendar permissions.
- **Resolution:** Added Contacts, sharing, preferences, and Tasks read and write scopes.
- **Regression/evidence:** Default, group, domain, read-only, and write-kill-switch tests pass.

### BUG-019 - Destructive tools could bypass confirmation by definition error
- **Symptom:** A new destructive registration could accidentally omit confirmation.
- **Root cause:** Coverage previously checked only the smaller active catalog.
- **Resolution:** Enforce confirmation for every active draft, write, and destructive definition.
- **Regression/evidence:** Capability self-test checks all 74 active definitions.

### BUG-020 - Administrative scope could enter the expanded catalog
- **Symptom:** Broad Carbonio coverage risked crossing into operator functions.
- **Root cause:** User and admin APIs share related command families.
- **Resolution:** Retained name and permission rejection for admin, auth, password, session, and impersonation tools.
- **Regression/evidence:** Forbidden definition tests pass and four excluded domains remain explicit.

### BUG-021 - The planner could invent required mutation fields
- **Symptom:** A model might create an ID or recipient not supplied by the user.
- **Root cause:** Free-form model output was not constrained to tool schemas.
- **Resolution:** Send only the allowed schema catalog and require null when any field is absent.
- **Regression/evidence:** Registry validation rejects unknown, missing, mistyped, or oversized fields.

### BUG-022 - New writes lacked stale-target protection
- **Symptom:** Confirmation delay could make a preview obsolete.
- **Root cause:** Not every new handler performed action-time reads.
- **Resolution:** Added post-confirmation revalidation for messages, contacts, appointments, folders, identities, signatures, and rules.
- **Regression/evidence:** Mismatch branches reject before the final SOAP mutation.

### BUG-023 - Unsupported Tasks mutations could be falsely advertised
- **Symptom:** The target server rejects documented task commands.
- **Root cause:** Documentation support does not guarantee dispatcher support on this installation.
- **Resolution:** Keep five mutations unavailable and two reads compatibility-gated.
- **Regression/evidence:** Live safe probe returned `service.UNKNOWN_DOCUMENT` for task commands.

### BUG-024 - Release documentation hid third-party addon risk
- **Symptom:** Users could assume official Zextras support or endorsement.
- **Root cause:** Prior reports focused on technical limitations only.
- **Resolution:** Added explicit independent-addon status and operator and user risk acceptance.
- **Regression/evidence:** README and this release report contain the support boundary.

### BUG-025 - Tool documentation drifted from the registry
- **Symptom:** Planned and active tables no longer matched executable tools.
- **Root cause:** The matrix was manually maintained without registry parity enforcement.
- **Resolution:** Updated the matrix and retained active capability to registry equality tests.
- **Regression/evidence:** Automated output is active 74, planned 5, gated 4, excluded 4.

## Known limitations and open gates

- Files and Docs and Chats and rooms remain unavailable on this target server.
- Five Tasks mutations remain unavailable and Tasks read synchronization awaits authenticated UAT.
- Binary PDF, office, archive, image, audio, video, and executable attachment bodies are metadata-only.
- Recurring appointment mutation is rejected rather than guessing an occurrence.
- The planner cannot compensate for missing exact IDs or current metadata. It asks the user to
  perform a bounded read first.
- Large-mailbox capacity, representative RAG evaluation, PostgreSQL HA, multi-browser UAT, and
  Carbonio upgrade rehearsal remain site-specific gates.
- Third-party provider quality, retention, availability, price, privacy, and model behavior are
  outside this project's control.

## Deferred scope

- Carbonio administration, authentication, password management, account lifecycle, COS,
  domains, servers, queues, backup administration, impersonation, and direct mailbox storage.
- Files and Docs and Chats until supported official user-scoped APIs pass on this server.
- Task mutations until the target server exposes compatible commands.
- Autonomous background mutations and compact-panel confirmations.

## Installation, upgrade, rollback, and verification

Download the release archive and matching `.sha256` file from the GitHub release. Verify the
checksum, extract the archive, inspect `release.env`, and run `sudo ./install.sh`. The installer
uses versioned UI and gateway directories, installs the loopback Nginx route, and manages
`carbonio-ai-gateway.service` and `carbonio-ai-rag-worker.service`.

Before an upgrade, run the installed PostgreSQL backup helper and record the current gateway
symlink target. After installation run:

```bash
sudo /opt/carbonio-ai-assistant/bin/smoke-test.sh
systemctl is-active carbonio-ai-gateway.service
systemctl is-active carbonio-ai-rag-worker.service
```

Use `rollback.sh <approved-commit>` to return the UI and gateway symlinks to a retained release.
Use `uninstall.sh` only after a verified backup and review of its data-retention prompt. See the
README for complete provider setup, PostgreSQL setup, API-key rotation, upgrade, rollback,
uninstall, troubleshooting, and user workflow instructions.
